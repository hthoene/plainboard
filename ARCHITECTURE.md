# Architecture

```
┌──────────────────────────── docker compose ─────────────────────────────┐
│ app  (FastAPI + React SPA)                          127.0.0.1:8080       │
│  api/            REST + WebSocket (UI), /api/internal (runner callbacks) │
│  services/       domain logic, shared by REST API and agent tools        │
│  tools/          agent tool registry (single source of truth)            │
│  orchestration/  run queue, context/compression, prompts, scheduler      │
│  SQLite (WAL) + Alembic · uploads volume                                 │
│        │ POST /runs  (RunSpec → NDJSON RunEvents)      ▲ tool calls       │
│        ▼                                               │ (per-run token)  │
│ runner  (internal only; user `agent` with sudo)                          │
│  providers/      claude_code (Agent SDK) · codex (app server) · mock     │
│                  endpoints: model servers and hosts, in claude_code's     │
│                  harness (translate.py for Chat Completions)             │
│  tool_bridge.py  proxies tool calls to the app; local tools (files)      │
│  workspace.py    /workspaces/<project>/<agent>/<repo> or a shared folder  │
└──────────────────────────────────────────────────────────────────────────┘
protocol/  shared pydantic models (RunSpec, RunEvent, ToolDef, ...)
```

**The app is the brain, the runner only executes.** The app decides what an agent sees (system prompt,
resumed session or summary, tools, MCP servers, credentials) and sends a `RunSpec`. The runner runs it
with a provider and streams normalised `RunEvent`s back. Agents get full control of the runner
container, but the app, its database and its secrets stay out of their reach. Each run gets a random
token that is valid only while the run lasts and only for that run's project and agent.

## Core concepts

| Concept | Where | Notes |
|---|---|---|
| Ticket (`Task`) | `models.py`, `services/board.py` | Never assigned to agents. Statuses live in `TaskStatus`. |
| Public API keys | `models.PublicApiKey`, `services/api_keys.py` | Several labelled keys per project for `api/public.py`. Only the hash is stored (the key is shown once); `last_used_at` is written at most hourly. |
| Customer texts | `task.customer_title`, `task.customer_description`, `api/public.py` | Short public title and description on a ticket, mostly written by the manager. `GET /api/public/tasks` with a project key returns only tickets with a customer title, and only these texts, number, status and date. |
| Assignment | `run_manager.delegate`, `run_manager._assignment_turn_ended`, `tools/team.py` | A work order for one member, optionally linked to a ticket: one piece of work with one report. It stays open while a job started for it is running (`job.assignment_id`): the job's result starts the turn that continues it, and only the turn after which nothing of it runs any more closes it and sends the report, with its time split (`timing.ledger`). An agent has one open assignment at a time; its next one waits. `delegate` refuses a second assignment for a ticket with open work unless it is another, independent part (`parallel`). |
| Task list (`Todo`) | `services/todos.py`, `tools/todos.py`, `features/team/TodoDialog.tsx` | Planned work per team member: title and a Markdown description. The manager adds, edits, moves and deletes items; members see their own list and mark items done. Agents only see open items: titles in the turn (never the system prompt, so the cache stays valid), and within a session only when the list changed (`conversation.todos_shown`); details via `get_todo`. Done items move to the archive after 7 days and are deleted after 90 (scheduler). A list does not start a run. |
| Decision | `services/decisions.py`, `tools/board.py` | A question from the manager to the user on a ticket, with options to click and attachments for the user's review. The answer becomes a ticket comment and an inbox update that wakes the agent that asked. If the user answers in chat, the manager records it with `resolve_decision`. |
| User action | `task.user_action`, `services/board.py`, `tools/board.py` | Something only the user can do for a ticket (e.g. test on a phone), set by the manager. The ticket stays highlighted until the user marks it done, which adds a comment and wakes the manager. |
| Board marks | `project.label_colors`, `services/board.sort_column`, `tools/board.py` | The manager gives a label one color across the board (`color_label`) and orders a column (`sort_tickets`). |
| Limit forecast | `services/limits.py` | Reports only give the current utilization, so each report adds a weekly window's new peak to a per-day total (kept with the limits in `Setting`). Rate: median of the days with use × share of such days over up to 7 complete days; with fewer than 3 days, the pace of this week so far. |
| Board check | `services/board.in_flight`, `services/board.idle_in_progress`, `prompts.board_check` | The manager's state comes from the database, not from its memory. Every manager turn lists what is in flight (open assignments with their state, branches on their way to the base branch), tickets in progress that nothing is happening on (no active run, open assignment, branch being landed, open decision or user action), free capacity (`board.capacity`) and the open tasks per member. `delegate` moves a ticket to in progress. |
| Statistics | `services/stats.py`, `services/timing.py`, `task_transitions`, `features/stats/` | The view's **Speed** section shows how fast finished work reaches the base branch and what it costs (branches landed, hand-over to landed, check runs, cost per landed branch, landing repairs), day by day and for the period against the same number of days before (`StatsPeriod`). Days on which PlainBoard itself started with another version are marked (`version.note_start` keeps that history), so what an update changed can be read off the numbers. `stats.work_report` (the download in the view) breaks runs down per agent, trigger, ticket, day and provider account (tokens, cache reads and writes, turns, time working and waiting), counts tool calls and adds the time overview (work against waiting, slow commands by their first two words, check runs for landing against branches landed), so a change of the system can be compared before and after: numbers and tool names only. Tickets per day come from `TaskTransition`, written on every status change and kept after a ticket is deleted. |
| Review | `project.review_days`, `services/board.unmarked_in_review`, `services/board.accept_reviews`, `prompts.review_line` | Review is only for what the user has to look at: the ticket says what in `user_action` (or has an open decision), everything else goes straight to done. `update_task` says so when a ticket lands in review without that, every manager turn lists such tickets, and the scheduler moves them to done (with a system comment, no agent turn) once they lay there unchanged for the project's days. |
| Archive | `task.archived_at`, `project.auto_archive_days`, `services/board.archive_tasks` | Done tickets leave the board after the project's days (the scheduler checks) or by hand. They keep their history and links; moving or restoring one brings it back. |
| Schedule | `models.Schedule`, `services/schedules.py`, `orchestration/scheduler.py`, `tools/automation.py`, `features/schedules/` | A prompt for an agent, once or by cron. With `skip_quiet` a run is left out when nothing happened in the project since the schedule's last run (`schedules.quiet`: no turn but its own, no ticket moved, nothing in the work log), so a status report costs no turn for "nothing new"; the work log notes it (`schedule.skipped`), and `last_run_at` stays the last run that happened. Schedules of a paused project pass without a turn. |
| Project language | `project.language`, `prompts.language_rule`, `prompts.language_note`, `update_project` | What people are written to in (section `language` of the briefing). Without one an agent answers in the language of what it read last, which after a night of notices is English: the manager's turn carries one line asking it to set the language until it has (`language_note`). New projects get that as part of their first ticket. |
| Users and access | `models.User`, `models.ProjectMember`, `services/users.py`, `services/access.py`, `api/deps.authorize`, `features/settings/UsersEditor.tsx`, `features/projects/MembersEditor.tsx` | People sign in with an account of their own (scrypt hashes; a signed cookie that names the user, the user's `session_version`, which a new password or switching the user off raises, and a session, `models.UserSession`, which signing out deletes, `services/sessions.py`). An **admin** runs the installation (settings, subscriptions, general secrets, users, read keys) and sees every project. Everyone else sees the projects they are a member of, as a **viewer** (reads everything, changes nothing), a **member** (works: tickets, chats, the team, notes, schedules) or an **owner** (also the project's settings, repositories, secrets, MCP servers, public API keys and members; may delete it). Whoever creates a project owns it; creating one takes `may_create_projects`, because projects use the installation's subscriptions. What a role may do is one table, `access.RULES`: a rule per route path (the longest matching beginning wins), with the need for reading and for changing, and for project routes the path parameter or the row that names the project. `authorize` is a dependency in front of every API router and checks it before the endpoint runs; sockets check with `deps.socket_role`. A route without a rule is for admins only and fails `test_every_route_has_a_rule`, so a new endpoint is never open by accident. A project the user has no part in answers 404, not 403. A read key reads what an admin reads. Where several people work in a project, what one writes carries the name (`users.author`: `[Name]` in front of a chat message, `comment.author_name`), for the agents; alone, nothing is added to the text. The chat itself never shows that bracket: a chat message knows its writer (`runs.author_name`, in the message as `meta.author`), and the UI shows name and profile picture above it (`MessageItem.writtenParts` also splits what several people wrote for one turn). A profile picture is a small square the browser cuts (`components/Avatar.tsx`), kept in `users.avatar` and served at `/api/avatars/{id}?v={avatar_version}`; agents have none. The limit: all agents on one runner share it, so a member who chats with agents can have them read what that runner holds (a project on an external runner of its own is kept apart). Roles are for people you trust with the installation. Whatever a person does in the UI that an agent is told about carries the name where several people work in the project (`users.author`, `prompts.person`): chat, comments, an answered decision, a finished user action, a ticket handed over. Seen without it: a friend answered a decision, the manager read "User decided" and wrote it down as the owner's. |
| Settings in the UI | `components/SettingsLayout.tsx`, `features/projects/ProjectSettings.tsx`, `features/settings/SettingsDialog.tsx` | Two places, each a list of sections with one open, and the same names in both and in the wizards. **Project settings** is a view in the navigation for the project's owners (General, Repositories, Team, Board, Secrets, Members, Public API, Advanced); a repository's own settings open from its row there. **PlainBoard settings** (the gear) is the installation's: everyone's own account, and for admins People, Subscriptions, Models, Code access, Pace, Secrets, General, Read access. A section that is a form saves with its own button; lists save each change at once and say so. |
| Set-up | `users.setup`, setting `setup_done`, `features/auth/Login.tsx` (`CreateAdmin`), `features/onboarding/` | An installation without users is not set up: the first person to open it creates the first admin in the browser. On a server `PLAINBOARD_PASSWORD` is the setup password that person must know (it has no other use any more). The admin then goes through the basic settings once, one decision per step with a recommendation: subscriptions (tested when going on), default models, code access, pace, general secrets, further people; `setup_done` remembers it (migration `0040` sets it where projects exist). A new project is a wizard too (`ProjectWizard`): it exists after the first step, so repositories, the manager's model, the project's subscription (`project.account_id`: its agents run on it unless an agent has its own), secrets and members are saved where they belong right away, with the editors the settings use. |
| Account | `models.Account`, `services/accounts.py`, `features/settings/AccountsEditor.tsx` | Several subscriptions or API keys per provider (encrypted, write-only). `accounts.pick` chooses per turn: the agent's pinned account, else the one of its last turn while nothing better is free (the prompt cache is per account), else in this order: subscriptions below 95 % (most room first), the rest of nearly full subscriptions, API keys, used-up subscriptions. Plan limits are stored and shown per account. They arrive with the turns of an account, are read when the UI asks, and every 15 minutes by `limits_watcher` for all subscriptions, so one that is not in use is not shown as it was hours ago. On the runner each Codex account has its own Codex home (`Credentials.codex_account`) whose `sessions` link to the default home's, so threads resume under any account. Claude accounts differ only in their token. A project can be limited to some accounts by an admin (`Project.account_ids`, `PUT /api/projects/{id}/accounts`, `accounts.limit_project`): `pick` then never returns another one, pins outside of them are refused (`check_pin`), and a turn on a provider the project has no account for fails with that reason (`shut_out`) instead of using one from outside. |
| Secrets | `models.Secret`, `services/secrets.py`, `Credentials.secrets` | User-defined environment variables for agents (global or per project; the project wins). Encrypted, write-only in the API. The runner sets them for the agent's shell, jobs and setup script, below git and auth variables. Agents see names and descriptions in the system prompt; values are replaced by `[secret NAME]` in stored messages and job reports. |
| Chat attachment | `services/board.py`, `api/chat.py` | A file sent with a chat message: an `Attachment` without a ticket, listed on the `Run` and in the user message's meta. The agent gets its path under `/uploads` in the turn and opens it with its file tools. |
| Preview | `services/preview.py`, `api/preview.py`, `api/guard.py` | `/preview/<port>/…` is proxied to `<runner host>:<port>` (HTTP streaming and WebSockets). A port opens only while a server job runs that listens on it (`preview.Owners`: running jobs no assignment waits for, and every port the runner finds them listening on, `/jobs/listening`; asked again after 5 s, at once when that job ended), and only for people with a role in that job's project, admins, and holders of that project's share of the port. A preview is agent code, so it never runs as PlainBoard: with `preview_origin` (`PLAINBOARD_PREVIEW_ORIGIN`) it is served only there (`guard.Guard` serves nothing else on that host; PlainBoard's address forwards with a token for two minutes and one port, `/api/public/preview/<port>/enter`, which becomes that origin's cookie for the port, bound to the PlainBoard session); without it previews run on PlainBoard's own address as before, unless `preview_sandbox` (`PLAINBOARD_PREVIEW_SANDBOX=true`) gives every preview response the CSP `sandbox` without `allow-same-origin` (an opaque origin: no PlainBoard cookies or API, no storage, and its subrequests carry no login, so a private preview loads no more than its page). The manager can share a port for a limited time (`share_preview`, `models.PreviewShare`): public, or with a password (form posts to `/api/public/preview/<port>/unlock`, which sets a signed cookie per port); the runner's own port and ports below 1024 are refused. The server sees `Host: localhost:<port>` at the root and never the session cookie. What it gets wrong because of that is repaired: `Location` headers get the prefix; a request whose `Referer` is a preview page is redirected (307) under that prefix before any other route; without a usable `Referer`, a part of a page that is neither PlainBoard's API nor one of its files goes to the last opened preview; WebSockets to the root follow the `plainboard_preview` cookie (set when a preview is opened as a page); `Set-Cookie` loses `Domain` (and `Secure` without HTTPS) and can't replace PlainBoard's cookies; a referrer policy that hides the page from its own site is relaxed; `Strict-Transport-Security` and `Clear-Site-Data` are dropped. A page that reads its own address (client-side routing) can't be repaired from outside: such a server is given the base path `/preview-base/<port>/`, a second prefix that is passed on unchanged. On the preview origin all previews still share one origin; one per preview would take a subdomain per port. |
| Request guard | `api/guard.py` | Outermost middleware: on the preview origin only previews; a change (not GET/HEAD/OPTIONS) whose `Origin`, else `Referer`, is not PlainBoard's own host (`Host` or `X-Forwarded-Host`) or `allowed_origins` is refused with 403, except token routes (`/api/internal`, `/api/public`) and previews (requests without either header are no browser's); bodies are capped by `Content-Length` and while they stream (10 × `max_upload_mb`, the import `max_import_mb`); HSTS on HTTPS answers (`X-Forwarded-Proto`, `hsts`). Sockets check `guard.origin_ok` themselves (`deps.socket_role`, the preview socket). The login cookie is `Secure` over HTTPS (`secure_cookies` forces it). Attachments open inline only by content (`board.inline_type`), always with `nosniff` and a CSP sandbox (not for PDF, whose viewers don't open under it). |
| Running previews | `runner/ports.py`, `services/preview.running`, `GET /api/projects/{id}/previews`, `features/browser/Previews.tsx` | Which web servers run is found, not told: a job's shell leads a session of its own, so the runner reads from `/proc` which listening sockets belong to a job's processes, asks each port once whether a web server answers (and for its page title), and remembers the answer. A server that answers nothing at its root but at `/preview-base/<port>/` has that as its base path (`JobPort.base`): the list opens it there. A job that answers on a port the app reaches keeps its ports on 127.0.0.1 to itself: they are what stands behind it (a backend behind a gateway, on another port after every start), and a page opened directly there breaks when that part is replaced. The app lists them for the project's servers (running jobs no assignment waits for) with their share; the UI asks every 10 s while a job runs at all. Shown in the sidebar and on the start page of the Browser view; a member stops one there (`RunManager.stop_job(by=...)`: the job's agent reads it with its next turn). Not found: a server that detaches itself into its own session, or runs as another user. |
| Pause everything | `services/pause.py`, `RunManager.pause_all`/`resume_all`, `/api/pause`, `features/settings/PauseEditor.tsx` | For an update or a restart: all projects come to rest, by a mechanism, with no manager turn. Every member is paused as `pause_team` does (the ids are remembered in the setting `pause`, so resuming enables exactly those), running turns get the wind-down notice (managers too, which stay enabled), and a gate holds everything else: the dispatcher only starts turns that wrap up (`stop_requested_at`) and the answers they wait for, and the landing watcher lets no new train leave. Background jobs are not left to the agents: `RunManager._rest_jobs` stops the jobs of every agent without a turn at once and those of a wrapping-up agent when its turn ends (servers of previews included; the restart ends them anyway), and one inbox note per agent says which, so it starts again what it needs with the turn it has anyway. `pause.status` counts what still moves from the database (running turns, jobs an assignment waits for, check runs in the runner); none left means at rest. The setting survives the restart (`RunManager.start` reads it). Admins pause and resume; everyone sees the band. |
| Standstill | `services/standstill.py`, `orchestration/standstill.py` | Every manager turn shows the free slots, but no prompt can start a turn: a manager whose last turn ordered nothing, with nothing running that would report back, is never woken again. A watcher without a model looks at the boards every two minutes: tickets to do or in progress that nothing happens on and that don't wait for the user (`board.untouched`), a free slot and an idle member, 15 minutes after the manager's last turn. Then the manager gets one update with exactly that (and how long nothing was ordered) and decides. The same tickets are told at most twice (`standstill.is_news`): once while other work runs, and once more when no assignment is open at all; other tickets not within the hour. A ticket that waits for the user is not counted once the manager has set its `user_action`, which the update asks for, so a project with nothing to start, or one that works step by step on purpose, costs nothing or next to nothing. Where the project goes on with its Backlog (`Project.continue_with_backlog`, the default; a switch in the project settings and in `update_project`), its tickets are ready work too, after To do, the most urgent first: the update names them, because a manager told to never rest has been seen to judge thirty of them from memory. The rule itself is a briefing section of its own (`prompts.BACKLOG_NEXT`/`BACKLOG_LATER`), so switching it sends a running session four lines, not the guide. A ticket that stops being ready is forgotten, so standing ready again later is news. Off while everything is paused, at limit 0 and without auto-wake. |
| First steps | `services/projects.FIRST_STEPS`, `ProjectCreate.first_steps`, `features/onboarding/ProjectWizard.tsx` | A project made in the UI starts with two tickets in To do: find out with the user what it is about, then propose a team (a strong model plans and reviews, a mid-range one builds, the most important core work on a strong one; no model is named, the manager reads the installation's models and their classes with `list_models` and takes the newest), the parallel limit and how finished work lands per repository, and set it up after the user's yes. All of it is a recommendation the user may overrule. The manager reads of them with its first turn (an inbox note; no turn is spent). Not for a project made over the API or brought from another PlainBoard. |
| Moving a project | `services/transfer.py`, `POST /api/projects/{id}/export`, `POST /api/projects/import`, `features/projects/MoveProject.tsx` | A project as one zip: `project.json` (the rows of its tables as they are) and `files/` (attachments). The tables are described, not coded one by one (`TABLES`): which rows belong to the project, which columns point at other rows (ids are new on the other side), which hold credentials, what starts anew. Credentials are decrypted with the installation's key and travel only sealed with a passphrase (scrypt, Fernet); otherwise the import names what is missing. Unknown columns are dropped and missing ones take their default, so close versions understand each other. Left behind: users, subscriptions, runs, jobs, landings, the provider sessions (a chat goes on from its summary and messages). On import open assignments are cancelled with a note, schedules get their next time from now, and nothing starts. **A new table or a new column that points at another row needs its entry in `TABLES`.** |
| Database | `config.database`, `db.py`, `migrate.py` | SQLite in the data volume by default; PostgreSQL when `PLAINBOARD_DATABASE` names one (driver: psycopg, async for the app and sync for the migrations). The migrations up to 0040 were written for SQLite: an empty PostgreSQL database is created from the models (`create_all`) and stamped at head, and runs every migration from then on, so **a new migration must work on both** (no SQLite-only SQL; booleans compared with true/false, not 1/0). Queries stay within what both understand: JSON through SQLAlchemy's accessors (`column["key"].as_string()`), no `json_extract`, `strftime` or `GROUP BY` shortcuts. The whole test suite runs against PostgreSQL when `PLAINBOARD_DATABASE` is set in the test environment (every test empties the database). SQLite-only: the read-only SQL of `services/db_read.py` (it relies on SQLite's authorizer). SQLite has one writer: between a write (`flush`, or a changed row and the next query) and its commit every other write waits, of every request and every agent. So nothing slow happens in between, above all no call to the runner (git, a model): commit first, call, then store the result. Seen: a train's row was written before the runner merged its branches, and for those nine seconds a click in a ticket hung and turns started late. The tests check it: `FakeRunner.database_free` fails a test whose code calls the runner with a write waiting. |
| External runner | `models.Runner`, `Project.runner_id`, `orchestration/runners.py`, `orchestration/tunnel.py`, `api/runners.py`, `services/runners.py`, runner `connect.py`, `protocol/tunnel.py`, `features/settings/RunnersEditor.tsx`, `features/projects/ProjectRunner.tsx` | A project runs on the built-in runner (`runner_url`) or on an external one, a runner on another machine that connects **out** to PlainBoard: one WebSocket to `/api/runners/connect` with its token (`PLAINBOARD_URL`, `PLAINBOARD_RUNNER_TOKEN`; sha256 of the token stored, shown once), so that machine needs no inbound port, TLS or DNS. Everything the app asks of it goes back through that socket: `TunnelTransport` is an httpx transport, so `RunnerClient` and the preview proxy are unchanged (not connected is a `ConnectError`, a broken line a `ReadError`), and `Tunnel.open_socket` carries the browser window's and previews' sockets for `relay`. The wire format is in `protocol/tunnel.py`: JSON control frames per stream, bodies and socket messages as binary frames; a URL port is a port on the runner's machine, none its own API. The runner forwards each to 127.0.0.1. Both sides ping every 15 s and drop a line silent for 45 s (half-open; under proxies' idle timeouts, Cloudflare ~100 s); the runner reconnects for ever with backoff and jitter up to a minute, and slowly (5–10 min) after the app closed with `CLOSE_REFUSED` (unknown or revoked token), `CLOSE_REPLACED` (a newer connection with the same token took over: the newest wins) or `CLOSE_PROTOCOL` (another tunnel protocol; a mere version mismatch is only shown). **Breaks:** a turn on an external runner does not end with its stream: the runner keeps its lines (`runner/runlog.py`, the last 20 000 lines / 8 MB) and `RunnerClient.stream_run` waits up to `RESUME_SECONDS` for the runner to be back and goes on with `GET /runs/<id>/events?after=<lines read>`: the count it has read is the acknowledgement, so no event is lost or repeated. 404 there (the runner was started anew: its hello carries a new `instance`) or 410 (more was missed than is held) ends the turn as a broken stream, like a restart of the built-in runner; its assignment goes on with the next turn. Jobs and servers run on through a break; the job watcher skips a runner that is away and reports jobs a restarted one no longer knows as lost. At every connect the app cancels turns the runner runs that no task here follows (after an app restart, which ends its turns as before; the runner itself cancels a turn nobody followed for 10 min). While a runner is away its projects' trains and branch tidying wait (`LandingWatcher._repo`, `BranchTidy`), and starting a job, a preview or the browser window answer at once that the runner is not connected. Agents' tool calls go straight to `PLAINBOARD_URL/api/internal` (the per-run token), not through the socket. `Runners` maps project → runner in memory (loaded at start, changed by `runners.assign`) and is asked at every call that is a project's: turns, cancel/notify, jobs (`job_watcher` asks each runner for its jobs), `check_turns` (per runner; one that is away counts its turns as alive), trains and the base guard (`landing`), tidy, `merge_when_green`'s head, summaries, previews (`preview.Owners` keeps every project per port, since ports repeat across runners; a viewer gets the one of a project they have a part in, else the one that shares it), the browser window, file removal, `list_cleanup`/`delete_cleanup` (the projects of that runner only). What is the installation's stays on the built-in runner: providers, plan limits, sign-ins, the update check, the Storage page and the cleanup watcher (which counts only the built-in runner's projects). So a project's credentials and secrets only ever reach its own runner. While an external runner is away the dispatcher leaves that project's turns queued (`Runners.ready`); a stream that broke off ends like one a restart cut off; after `AWAY_TELL_SECONDS` the managers hear it once (`Runner.away_told_at`, `RunManager.check_runners` in the job watcher's look) and again without a turn when it is back. An external runner has no uploads volume: before a turn the project's attachments it lacks are copied (`/uploads/missing`, `PUT /uploads/<name>`, remembered per connection). A project moves only while it has no running turn, job or check run (`runners.busy`): workspaces don't move and the home is per runner. The runner image knows its commit (`/etc/plainboard-commit`) and says it in its hello; Settings > Runners shows a mismatch with the app's. `runner_id` is reset when a project is moved to another PlainBoard (`transfer.TABLES`); runners are installation data. |
| Browser window | runner `browser.py`, `api/browser.py`, `api/relay.py`, `features/browser/BrowserView.tsx` | A Chromium in the runner, one per project, shown in PlainBoard: there a page of an agent's server is at `localhost:<port>`, as it believes, so everything works that a path or a shared address breaks (routing, storage, cookies, sign-in redirects to localhost). The runner drives it over the DevTools protocol (`/browser/<key>`, a WebSocket): frames of the page as JPEG down, input and navigation as JSON up (the messages are listed in `browser.py`). The picture keeps pace with the viewer: the browser makes the next frame only when a viewer has confirmed the last, so a slow line gets fewer frames, never old ones; frames are small while the page moves and one sharp picture follows when it rests. The app only checks the login and relays the socket (`/api/projects/<id>/browser`); it does not read what passes. Only for the signed-in user, never for a shared preview. ### Run lifecycle (`orchestration/run_manager.py`)
1. `enqueue` creates a `Run(queued)`. The dispatcher starts it when the agent is idle and fewer member
   runs of its project are active than the project's limit (`projects.parallel_limit`: the project's own
   `parallel_agents`, else the setting `max_parallel_runs`). Every project counts by itself, so one busy
   project never leaves another one waiting. The limit is about members only: a manager's run
   starts as soon as the manager is free, also at limit 0 (which pauses the members), because the
   user and the team wait for it. Nested `ask_agent` runs bypass the limit, so a run that is waiting
   can never starve the run it waits for. A wait inside a turn never holds back an answer either:
   when the user writes to an agent whose turn sits in `wait_job` or `ask_agent`, that wait ends
   (`_end_waits`; the job goes on, the answer comes as an update), and a teammate's question ends a
   wait for a job. A manager can change the number of its own project
   (`set_parallel_agents`), up to the user's `manager_parallel_limit` (0: not at all).
2. `_prepare`: link a wake-up to the agent's open assignment, consume the inbox, store the user
   message, start a new context for a member's assignment on another ticket, build the turn
   (`ContextManager.build_turn`), issue a run token, then assemble the `RunSpec`.
3. `_stream`: persist assistant texts and tool calls, publish text deltas over the WebSocket, and track
   context size from usage events.
4. `_finish` → `_after_run`: route results (answer to the asker; for an assignment's turn either keep
   the assignment open for its job or close it: report to the requester's inbox, wake the requester;
   the report stays with the assignment, which the ticket shows, and is no comment), then `maybe_compress`. After every run `_settle` makes sure an open assignment
   that waits for nothing any more gets the turn that finishes it (also after a restart).

Queued runs start in this order: nested `ask_agent` runs, then chat messages from the user, then work
that has been started (wake-ups, repairs of branches for landing), then the rest by age. An agent's
next assignment does not start while it has an open one. A chat message for a working agent is also given to its running turn as a notice (`prompts.chat_notice`,
seen after the current tool call, nothing is interrupted) and stays queued as the next turn, so it is never
lost. Until that turn starts the user can delete the message (`withdraw_chat`). A wake-up whose updates an
earlier turn already consumed is dropped.

A restart fails running runs, but it is not a failure of the work: an interrupted assignment stays open
and its agent goes on in the same session, with a note that its last step may be half done
(`_recover_interrupted`). No manager turn and no new assignment are needed. Only an assignment that
restarts keep cutting off (`MAX_RESTART_RESUMES`), and an interrupted turn outside an assignment, are
reported: to the requester, or to the manager for its own turn.

A job outlives its run: the stop button of a run does not touch it. If a job of an assignment is still
running when its turn ends, the assignment stays open and goes on when the job ends. Cancelling an
assignment (`cancel_assignment`) stops its jobs, also when it has no turn at the moment.

A provider's own background work belongs to the turn. Claude Code runs sub-agents in the background, and
an agent with nothing else to do ends its turn while they work; the session goes on by itself when one
reports. The runner does not take that end as the turn's result (`claude_code.BackgroundWork`, fed by Claude
Code's Stop hook, which lists what is in flight): it keeps the session open until no sub-agent is left, with
no model turn spent on waiting. A message for the waiting agent is given to it as a prompt at once. After
20 minutes without any sign of life the agent is told to finish without. Background shells are not waited
for: a dev server never ends.

`wind_down` stops an agent safely. A running turn gets an urgent notice: it arrives after the current tool
call, and a tool call still open after 60 seconds is interrupted (`claude_code.UrgentNoticeWatch`). An agent
with no turn but running jobs gets a turn for stopping them, even if it is paused. A paused (disabled) agent
keeps its assignments: the one it was working on stays open, queued ones stay queued, and all go on when
it is enabled again (`resume`). Stopping an agent without pausing it drops its queue and ends with a report.

`ask_agent` blocks on a future. A wait-for graph between agents rejects cycles, and depth and timeout
limits apply. An answer that arrives after a timeout goes to the asker's inbox instead.

### Context & compression (`orchestration/context.py`)
- Every turn re-reads its whole context, so its size is what a turn costs. A member's context belongs to
  a piece of work: an assignment for another ticket starts a new session (`new_topic`,
  `conversation.session_topic`) with the system prompt, the assignment and a line on its last
  assignments. Nothing is summarized for that; what must outlive a ticket is in the member's own notes,
  the project notes, the ticket and the repository. Further assignments for the same ticket, wake-ups,
  messages and the user's chat continue the session. The manager keeps one session.
- With a session: resume it (prompt caching, full tool history inside Claude Code). The system prompt
  is **frozen per session** (`conversation.system_prompt`) so the cached prefix stays valid. If the
  briefing changes mid-session (team, pinned notes, repositories, instructions …), only the changed
  sections are sent as a `[Briefing update]` at the start of the next turn (`prompts.briefing_update`).
  A new session (first turn, after compression or reset) gets a fresh system prompt with the current state.
- Above `agent.context_limit_tokens` (default 120k): summarise every uncovered message except the last
  `keep_recent_messages` text messages, using `agent.summary_model` via `runner /complete`. Large
  transcripts are summarised in chunks. Then drop the session and record a `summary` message.
- Fresh session: system prompt + `## Memory` (summary) + recent messages verbatim (truncated) + the new
  turn. This also works unchanged for stateless providers.
- A provider may compact its own session, e.g. mid-run near the model's context limit (`compaction`
  event). The session continues, a `summary` message without text is recorded, and the next turn
  re-sends what differs from the frozen prompt (`conversation.session_sections`), because earlier
  briefing updates may be lost. This also applies when `context_limit_tokens` is above the provider's
  own threshold: then the provider compacts and PlainBoard's compression does not start.

### Prompts (`orchestration/prompts.py`)
The system prompt is stable (cache-friendly): role, area, guide, workspace, instructions, team roster,
pinned notes, own notes, memory. Volatile data such as the current time and inbox updates goes into the user turn.
The manager uses the `board` toolset: a short custom prompt and no Claude Code preset, with shell and
file editing for small tasks it would cost more to delegate. Workers use
`full`: the Claude Code preset with the PlainBoard part appended.

**Add an agent tool.** Add a decorated function to a module in `app/plainboard/tools/`:

```python
class MyArgs(BaseModel):
    number: int

@tool("my_tool", "What it does (shown to the model).", MyArgs, roles=(MANAGER,))
async def my_tool(ctx: ToolContext, args: MyArgs) -> str:
    ...  # use services, return compact text
```
The schema is derived from the args model, stripped of titles, and sent with every run. The runner
needs no change. Tools that need the agent's filesystem are declared with `local_tool(...)` and
implemented in `runner/plainboard_runner/tool_bridge.py`.

**Prompt cache.** The cached prefix is tools, then system prompt, then messages: a changed tool
definition or system prompt invalidates everything after it, so both stay stable within a session. The
cache is per provider account and model. Claude runs ask for the one-hour lifetime
(`ENABLE_PROMPT_CACHING_1H`), because turns of one agent are often more than five minutes apart.

**Add a provider.**
1. Implement `Provider` in `runner/plainboard_runner/providers/<name>.py`: `info()` (models and efforts),
   `run(spec, bridge)` yielding `RunEvent`s and ending with a `ResultEvent`, and `complete(spec)`.
   Optional: `catalog()` (models the account offers), `limits()`, and `account()`/`login()`/`logout()`
   for a subscription signed in on the runner (the UI's device sign-in uses them).
2. Register it in `providers/registry.py`.
3. Add its credentials to `Credentials`, its sign-in kinds to `services/accounts.py` (`AUTH_MODES`, `fields`)
   and the accounts editor.

A model server or host that speaks the Messages or the Chat Completions interface needs none of
this: it is one line in `ENDPOINTS` (see below).

**Providers that are an address** (`providers/endpoints.py`): a model server of one's own (Ollama, LM
Studio, llama.cpp, vLLM), a model host (Gemini, OpenRouter, DeepSeek ...) or any gateway. Each line of
`ENDPOINTS` is a provider: a name, the usual address, whether it wants a key, and which of two
interfaces it speaks. The turn runs in Claude Code's harness (`EndpointProvider` is a
`ClaudeCodeProvider` with another environment), so tools, notices, sub-agents and the session work as
on Claude. A server that speaks Anthropic's Messages interface is talked to directly
(`ANTHROPIC_BASE_URL`). For one that speaks Chat Completions the harness is pointed at the runner
itself: `translate.py` (`/compat/<address>/v1/messages`) turns the request into a chat request and
the streamed answer back into Messages events. It keeps nothing but what a model wants back with its
tool calls (Gemini's thought signatures), guesses the prompt's size for the start of the answer (a
chat server counts it at the end, the harness reads its context there), and leaves out the answer
length for a server that refused it. The environment keeps the harness to what any server
understands (no beta fields, no tool search, no thinking request, the context window the account
names instead of the million tokens Claude Code assumes for an unknown model). No model names are
kept: the account names them, `Provider.models` asks the server. Cost is reported as 0.

On the app's side nothing names these providers. `ProviderInfo.endpoint` marks one; its accounts hold
address, key, models and context window (`Account.endpoint_url`, `models`, `context_tokens`), which
travel as `Credentials.endpoint_*`. `accounts.catalog` is the list agents choose from: the runner's
providers, of which an endpoint counts once an account names a model. `accounts.pick` takes an
account that offers the turn's model, so two servers of one provider work side by side.

A provider that can't call Python tools in-process can serve the bridge as a stdio MCP server
(`plainboard_runner/mcp_stdio.py`), as Codex does. Agents choose their provider; models of the same
`tier` stand in for each other when an agent changes provider (`services/agents.equivalent_model`).

**Codex.** `providers/codex.py` drives `codex app-server` (JSON-RPC over stdio; the CLI version is
pinned in the runner's Dockerfile), one process per run. Board tools come from `mcp_stdio`, messages
for a running turn go in with `turn/steer`, and the thread id is the session id. The default account's ChatGPT
sign-in lives in `~/.codex` (agent-home volume), further accounts in `~/.plainboard/codex-accounts/<key>`;
an API key is signed in to a separate Codex home.

The UI picks up models from `/api/meta`. If the provider has no server-side sessions, return no
`session_id`: the context manager then rebuilds every turn from summary + recent messages.

**Add a ticket status.** Extend `TaskStatus` (backend), `Status` in `schemas.py`, `STATUSES` in
`frontend/src/features/board/Board.tsx`, and the `taskStatus` texts in `en.json`.

**Add a design or a theme.** The look has two levels, both chosen in the browser (`lib/theme.ts`,
`features/layout/LookDialog.tsx`) and set on `<html>`: `data-design` and `data-theme`.

- A **design** is a look: its type, corners, shadows, and how the parts are drawn. Fahrplan is
  `frontend/src/index.css`, the base every component is written against. Every other design is one stylesheet in
  `frontend/src/designs/` (`classic.css` is the example to copy), imported in `main.tsx` and listed in
  `DESIGNS` in `lib/theme.ts` and in the pre-paint script of `index.html`. The first design listed
  there is the default for a browser that has not chosen: Classic. It is not layered, so it
  wins over the utility classes of the components. A design has three means, in this order of
  preference: tokens (`--font-sans`, `--radius-*`, `--shadow-lg`, `--font-weight-*` and its
  colours), the semantic classes (`.plate`, `.caps`, `.mk-*`, `.rule-b`, `.rule-t`, `.sq-hue`,
  `.prose-chat`), and the named parts (`data-part`: `side`, `topbar`, `tabs`, `main`, `panel`,
  `page-head`, `board`, `column`, `column-head`, `column-body`, `ticket`, `new-ticket`, `tag`, `facts`,
  `you`, `you-plate`, `agent`, `button`, `field`, `toggle`, `badge`, `modal`, `modal-head`, `menu`,
  `msg`, `msg-head`, `note`, `composer`, `error`; some carry state such as `data-for-you`,
  `data-role`, `data-status`, `data-variant`, `data-tone`, `data-priority`, `data-hue`).
- A **theme** is one block of colour tokens of a design (`[data-theme="…"]`); each design has a dark
  and a light one.

Components never branch on the design or the theme: no `dark:` variant, no palette colour, only the
semantic colours (`bg-bg`, `text-fg-2`, `border-line`, …). A new part of the interface that a design
should be able to draw differently gets a `data-part` name. `DESIGN.md` has the rules of Fahrplan.

**Add a UI language.** Copy `frontend/src/i18n/en.json` to `<code>.json` and register it in `i18n/index.ts`.

**Database changes.** Edit `models.py`, then generate a migration:
```bash
docker run --rm -v "$PWD":/repo -w /repo/app plainboard-app sh -c \
  "PYTHONPATH=/repo/app PLAINBOARD_DATA_DIR=/tmp/db python -m plainboard.migrate revision 'describe change'"
```
Migrations run automatically on startup.

## Testing
- `app/tests`: a `FakeRunner` executes tools through the real `RunManager`. It covers ticket hand-off,
  delegation with reports and wake-ups, `ask_agent`/`message_agent`, compression, schedules, tool
  scoping and settings.
  The `FakeRunner` also fails a test when it is called between a write to the database and its commit
  (`database_free`).
  The migrations run once per test run, not per test (`conftest.new_installation`): after the first
  test SQLite gets a copy of its file, PostgreSQL has its tables emptied. Per test they were most of its time.
- `runner/tests`: SDK event mapping, tool bridge, workspace safety, the mock provider over HTTP.
- End-to-end without credentials: set an agent's provider to **Mock** and use the directives
  `TOOL <name> <json>` / `SAY <text>` in messages.
